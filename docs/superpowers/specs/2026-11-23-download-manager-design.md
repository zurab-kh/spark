# Менеджер загрузок «Стрела» — дизайн

Дата: 2026-11-23
Рабочее название: **Стрела** (Strela). Название — моё решение, легко поменять.

## 1. Зачем

Пользователь сейчас качает через Free Download Manager, и FDM его не устраивает:
лагает, медленно грузит, задаёт много вопросов, зависает. Нужна своя программа,
которая **качает быстрее FDM** (это главный критерий) и при этом просто работает:
не тормозит, не зависает, ни о чём лишнем не спрашивает.

**Откуда качает пользователь:** в основном прямые публичные ссылки (зеркала,
сайты программ, CDN). Вход на сайт, cookies браузера и т.п. не нужны — поэтому
перехват из браузера не обязателен для v1.

## 2. Цели, не-цели, анти-цели

**Цели (v1)**
- Скорость загрузки не ниже FDM, а на серверах, которые режут скорость на одно
  соединение, — заметно выше (за счёт умной нарезки, раздел 5.3).
- Интерфейс никогда не подвисает: сеть и диск полностью вне UI-потока.
- Надёжная докачка: обрыв связи, перезапуск программы, падение процесса,
  перезагрузка ПК — загрузка продолжается с места, где остановилась.
- Ноль вопросов в обычном сценарии: вставил ссылку → качается в папку
  «Загрузки» под правильным именем.
- Лёгкость: быстрый запуск (< 1 с до окна), мало памяти в простое.

**Критерии успеха (проверяемые)**
- Бенчмарк (раздел 7): на наборе тестовых ссылок средняя скорость ≥ FDM;
  на локальном сервере с ограничением 1 МБ/с на соединение — полное использование
  доступных соединений и отсутствие «хвоста» в конце загрузки.
- UI-поток не блокируется дольше 100 мс ни в одном сценарии (включая 20 активных
  загрузок и 1000 записей в списке).
- Убийство процесса во время загрузки → после перезапуска загрузка продолжается,
  итоговый файл побайтово совпадает с оригиналом.

**Не-цели v1** (следующие этапы)
- Расширение для браузера (перехват кликов). В v1 только закладываем канал
  приёма ссылок извне (раздел 6.4), чтобы расширение потом просто подключилось.
- Торренты, видео с сайтов (YouTube и т.п.), FTP.
- Расписание, ограничение скорости, проверка контрольных сумм.
- Авто-обновление, установщик (v1 — портативная папка с exe).

**Анти-цели** (даже если всё работает — это провал)
- Модальные окна в обычном сценарии: «куда сохранить?», «вы уверены?»,
  «файл существует, заменить?».
- Реклама, телеметрия, регистрация, сетевые запросы кроме самих загрузок.
- Подвисание окна, «Не отвечает» в заголовке.
- Потеря уже скачанного при сбое.

## 3. Ограничения

- Windows 11. C# + WPF. Без админских прав.
- **Целевая платформа — .NET 10 (LTS).** У пользователя установлен .NET 8 SDK
  (8.0.423), но поддержка .NET 8 закончилась 10.11.2026 (нет патчей безопасности),
  а программа разбирает ответы чужих серверов. .NET 10 SDK ставится для текущего
  пользователя скриптом `dotnet-install.ps1` (без админа). Публикация —
  self-contained, чтобы программа не требовала установленного рантайма.
  (Моё решение; язык и UI-технология от этого не меняются.)
- Только поставляемые с .NET библиотеки + минимум сторонних (тесты: xUnit;
  трей: допустимо `Hardcodet.NotifyIcon.Wpf` или собственная обёртка над WinForms NotifyIcon — на усмотрение строителя).

## 4. Подходы (рассмотренные)

| Подход | Плюсы | Минусы |
|---|---|---|
| **C# / .NET 8 + WPF** ✅ выбран | .NET 8 уже установлен; быстрый сетевой стек (SocketsHttpHandler); нативный Windows UI; быстро писать | ~50–70 МБ памяти в простое |
| Rust + Tauri | 10–20 МБ памяти, максимальная эффективность кода | Rust и VS Build Tools не установлены (несколько ГБ); писать дольше; скорость загрузки та же — упираемся в сеть |
| Обёртка над aria2 | Самый быстрый путь к проверенной скорости | Чужой движок; нельзя сделать свою умную нарезку и замену медленных потоков |

Пользователь выбрал вариант 1. Обоснование: FDM тормозит из-за устройства
программы, а не языка; узкое место загрузки — сеть, а не CPU.

## 5. Движок загрузки (`Strela.Engine`, библиотека без зависимостей от UI)

### 5.1 HTTP-клиент
- Один общий `HttpClient` поверх `SocketsHttpHandler`:
  - `MaxConnectionsPerServer` — без практического ограничения (≥ 64);
  - `AutomaticDecompression = None` (иначе Range-запросы ломаются);
  - `PooledConnectionLifetime` ~ 5 мин; разумные таймауты подключения (~15 с);
  - **принудительно HTTP/1.1** (`DefaultRequestVersion = 1.1`,
    `VersionPolicy = RequestVersionOrLower`): при HTTP/2 все потоки идут через одно
    TCP-соединение, и обход ограничения скорости на соединение не работает.
- Редиректы следуем автоматически; итоговый URL запоминаем для докачки.
- User-Agent — как у обычного браузера (некоторые сервера режут нестандартные).

### 5.2 Разведка (probe)
GET с `Range: bytes=0-0` (запасной вариант — HEAD). Получаем:
- размер (`Content-Range` / `Content-Length`);
- поддержку диапазонов (ответ 206);
- `ETag`, `Last-Modified` — для проверки при докачке;
- имя файла: `Content-Disposition` (включая `filename*=` UTF-8) → последний сегмент
  URL (с URL-декодированием) → `download`. Недопустимые для Windows символы
  заменяются.

Если диапазоны не поддерживаются или размер неизвестен — однопоточная загрузка
(докачка в этом случае невозможна, при обрыве — перезапуск с нуля, без вопросов).

### 5.3 Нарезка и потоки (главное отличие от FDM)
- Настройка «соединений на файл»: по умолчанию **16**, диапазон 1–32.
- Минимальный размер куска для деления: **1 МБ** (файлы < 2 МБ качаются в 1 поток).
- Старт: файл делится на N равных кусков (N = min(соединений, размер / 1 МБ)).
- **Динамическое деление (work stealing):** когда поток закончил свой кусок,
  он находит кусок с наибольшим остатком; если остаток ≥ 2 МБ — делит остаток
  пополам: «владелец» продолжает до середины, освободившийся поток берёт вторую
  половину. Граница куска меняется атомарно; владелец читает её перед каждой
  записью и останавливается, дойдя до неё (лишние полученные байты отбрасываются).
  Итог: в конце загрузки нет «хвоста» на одном медленном соединении.
- **Замена медленных соединений:** раз в 2 с сравниваем скорость каждого потока
  с медианой. Если поток < 25 % медианы дольше 6 с и у него осталось ≥ 2 МБ —
  обрываем и переоткрываем соединение с текущей позиции.
- **Ограничение сервера:** если сервер отвечает 429/503 или рвёт новые соединения,
  уменьшаем число потоков для этой загрузки (не ниже 1) и запоминаем потолок
  для хоста на время сессии.

### 5.4 Ошибки и повторы
- Сетевые ошибки и 5xx: повтор с экспоненциальной задержкой (1, 2, 4 … 30 с),
  с учётом `Retry-After`. Ошибки одного потока не роняют загрузку.
- Загрузка переходит в состояние «Ошибка» только после ~2 минут непрерывной
  неудачи всех потоков или при окончательных ответах (403, 404, 410). В списке
  показывается понятная причина; кнопка «Повторить».
- Пропала сеть целиком → загрузки ждут и сами продолжаются, когда сеть вернулась
  (`NetworkChange.NetworkAvailabilityChanged` + обычные повторы).

### 5.5 Запись на диск
- Файл пишется во временный `имя.ext.strela` в целевой папке.
- Место резервируется сразу (`SetLength`).
- Запись позиционная и потокобезопасная: `RandomAccess.Write(SafeFileHandle, buffer, offset)`;
  у каждого потока свой буфер (256 КБ–1 МБ из `ArrayPool`), запись крупными блоками.
- Если на диске не хватает места — загрузка «на паузе» с причиной, без падения.
- По завершении: переименование в итоговое имя. Если имя занято —
  автоматически `имя (1).ext`, `имя (2).ext` … без вопросов.

### 5.6 Сохранение состояния и докачка
- Состояние каждой загрузки — JSON в `%LOCALAPPDATA%\Strela\downloads\{id}.json`:
  URL (исходный и итоговый), размер, ETag/Last-Modified, путь, список кусков
  (начало, конец, сколько записано), статус, даты.
- Сохраняется раз в ~2 с и при паузе/закрытии. Порядок: сначала `Flush` данных
  файла на диск, потом запись состояния (атомарно: во временный файл + замена).
  Состояние **никогда** не опережает данные — в худшем случае перекачаем пару секунд.
- При докачке сверяем ETag/Last-Modified/размер. Если файл на сервере изменился —
  начинаем заново (без вопросов, с пометкой в логе).
- Ссылки с истёкшим сроком (403 при докачке): v1 — статус «Ошибка: ссылка устарела»
  с возможностью вставить новую ссылку для той же загрузки (контекстное меню
  «Обновить ссылку»), прогресс сохраняется, если размер совпадает.

### 5.7 Очередь
- Одновременно активных загрузок: по умолчанию **3** (настраивается).
  Остальные ждут в очереди FIFO; порядок можно менять перетаскиванием или кнопками.
- Состояния: В очереди, Загружается, Пауза, Готово, Ошибка.

### 5.8 Как движок сообщает о прогрессе
Движок не шлёт событие на каждый пакет (это одна из причин лагов). Счётчики
байтов — атомарные; UI сам забирает снимок состояния по таймеру 4 раза в секунду.
Скорость — скользящее среднее за ~3 с, ETA от неё.

## 6. Приложение (`Strela.App`, WPF)

### 6.1 Главное окно

```
┌──────────────────────────────────────────────────────────────────┐
│ [ Вставьте ссылку и нажмите Enter...                  ] [Скачать]│
├──────────────────────────────────────────────────────────────────┤
│ Имя               Размер   Прогресс          Скорость   Осталось │
│ ubuntu-24.iso     5.7 ГБ   ███████░░░  68%   42 МБ/с    0:45     │
│ setup.exe         120 МБ   ██████████ Готово                     │
│ video.mp4         1.2 ГБ   ░░░░░░░░░░ В очереди                  │
├──────────────────────────────────────────────────────────────────┤
│ Всего: 42 МБ/с · Активно 1 · В очереди 1          [⚙ Настройки] │
└──────────────────────────────────────────────────────────────────┘
```

- Поле ввода: вставка одной или нескольких ссылок (по одной на строку) → Enter →
  сразу в очередь. Никаких диалогов.
- Список виртуализирован (держит тысячи записей без тормозов).
- Двойной клик по готовой — открыть файл; контекстное меню: открыть папку,
  пауза/продолжить, повторить, обновить ссылку, копировать ссылку, удалить из
  списка, удалить с файлом (единственное место с подтверждением — удаление
  файла с диска).
- Перетаскивание ссылки в окно — добавить.
- Тёмная/светлая тема по системной.

### 6.2 Буфер обмена
Включено по умолчанию, отключается в настройках. Когда в буфер копируется ссылка
http/https, похожая на файл (расширение из списка: архивы, iso, exe/msi,
видео, аудио, образы, документы и т.п.), — **немодальное** уведомление в углу
экрана «Скачать <имя>?» с кнопкой «Скачать», само исчезает через ~8 с.
(Моё решение: автоматически добавлять без подтверждения было бы сюрпризом при
каждом копировании ссылки; одно ненавязчивое уведомление — компромисс.)

### 6.3 Трей и запуск
- Иконка в трее с общей скоростью в подсказке. Закрытие окна при активных
  загрузках — сворачивание в трей; без активных — выход. (Моё решение.)
- Один экземпляр: повторный запуск выводит окно уже работающего.
- Опция «Запускать вместе с Windows» (выключена по умолчанию; реестр HKCU\Run).
- По завершении загрузки — короткое системное уведомление (отключаемо).

### 6.4 Приём ссылок извне (задел под расширение браузера)
`Strela.exe <url> [<url>...]` — если программа уже запущена, ссылки передаются
ей через именованный канал (named pipe) и сразу встают в очередь. Это же
позже использует расширение браузера (через native messaging).

Сообщение в канале — JSON: `{ "url": "...", "referer"?: "...", "headers"?: {...},
"cookies"?: "...", "fileName"?: "..." }`. В v1 используется только `url`, но движок
уже принимает необязательные поля для запроса, чтобы расширение потом
подключилось без смены протокола. (Моё решение.)

### 6.5 Настройки
Немодальное окно / панель: папка загрузок (по умолчанию системная «Загрузки»),
соединений на файл, одновременных загрузок, буфер обмена вкл/выкл, уведомления,
автозапуск. Хранятся в `%LOCALAPPDATA%\Strela\settings.json`.
Мелкая сортировка по папкам по типу файла — не в v1.

### 6.6 Логи
Файл лога с ротацией в `%LOCALAPPDATA%\Strela\logs` (ошибки сети, решения движка:
деление кусков, замены потоков, перезапуски). Только локально.

## 7. Проверка скорости и надёжности

### 7.1 Локальный тестовый сервер (`Strela.TestServer`, Kestrel)
Отдаёт файлы с поддержкой Range и умеет: ограничивать скорость на соединение,
задавать разную скорость разным соединениям (чтобы проверить замену медленных),
рвать соединения, отвечать 503/429, менять файл (ETag) между запросами, не
поддерживать Range. Используется в автотестах и бенчмарке.

### 7.2 Автотесты (`Strela.Engine.Tests`, xUnit)
Нарезка и динамическое деление (юнит), загрузка на тестовом сервере с проверкой
хеша, докачка после остановки и после «убийства» (отмена без сохранения +
перезапуск из состояния), изменение файла на сервере, сервер без Range,
повторы при обрывах, коллизии имён, разбор Content-Disposition.

### 7.3 Бенчмарк (`Strela.Bench`, консоль)
Качает список ссылок, печатает время и среднюю скорость по каждой. Сравнение с
FDM — вручную: те же ссылки, те же условия, результаты в таблицу
`docs/benchmark.md`.

Условия сравнения (моё решение):
- FDM запускает пользователь (он у него установлен); Strela.Bench — строитель
  или пользователь на той же машине и сети, попеременно, по 2 прогона на ссылку.
- FDM проверяется в двух режимах: настройки по умолчанию и максимум соединений
  на файл, разрешённый FDM. Strela — с настройками по умолчанию.
- **Пройдено**, если средняя скорость Strela ≥ FDM в обоих режимах, и ни на одной
  ссылке Strela не медленнее FDM больше чем на 10 %. Ссылки, где проигрыш
  больше, разбираются по логам (это и есть фаза подстройки; она ограничена
  этим набором ссылок). Набор реальных ссылок: несколько крупных публичных файлов
(дистрибутивы Linux с разных зеркал, тестовые файлы провайдеров) — подберёт
строитель.

## 8. Структура решения

```
Strela.sln
  src/Strela.Engine        — движок (без UI)
  src/Strela.App           — WPF-приложение
  tests/Strela.Engine.Tests
  tools/Strela.TestServer
  tools/Strela.Bench
```

Сборка: `dotnet publish` в портативную папку (framework-dependent, .NET 8 у
пользователя есть). Single-file — на усмотрение строителя.
